## String неизменяем

```java
String s = "Hello";
s = s + " world";     // старый объект не изменился — создан НОВЫЙ "Hello world"
```

Склейка в цикле создаёт новую строку на каждой итерации и копирует в неё всё накопленное — для текста длины n это O(n²) операций и гора мусора для GC.

```java
StringBuilder sb = new StringBuilder();
for (…) sb.append((char) b);         // меняет внутренний буфер
String result = sb.toString();
```

| | `String` | `StringBuilder` | `StringBuffer` |
|---|---|---|---|
| Изменяемый | ❌ | ✅ | ✅ |
| Потокобезопасный | ✅ (неизменяем) | ❌ | ✅ (`synchronized`) |
| Когда | почти всегда | сборка строки в одном потоке | на практике почти никогда |

:::interview "Вопрос с собеседования"
**Чем отличаются `StringBuilder` и `StringBuffer`?** — Оба — изменяемые строки. Методы `StringBuffer` синхронизированы (потокобезопасен, медленнее), `StringBuilder` — нет. В современном коде используют `StringBuilder`: собирать одну строку из нескольких потоков почти не нужно.
:::

:::note "А `+` вне цикла?"
`String s = a + ":" + b;` — нормально. Компилятор оптимизирует одиночную конкатенацию (с Java 9 — через `invokedynamic`/`StringConcatFactory`). Проблема только в накоплении в цикле. Для склейки коллекции есть `String.join(", ", list)` и `Collectors.joining`.
:::

## Чтение массивом

Каждый `read()` — обращение к операционной системе, а это дорого. `read(byte[])` за одно обращение заполняет целый массив:

```java
try (InputStream in = new FileInputStream(file)) {
    byte[] buffer = new byte[8192];                 // кратно 1024
    StringBuilder sb = new StringBuilder();
    int count;
    while ((count = in.read(buffer)) > 0) {
        sb.append(new String(buffer, 0, count));    // только прочитанная часть!
    }
}
```

`read(byte[])` возвращает **сколько байтов прочитано** (последний раз — меньше размера массива, затем −1). Если создать строку из всего массива, в конце окажется «мусор» от прошлого чтения ({{t j2 5:49:44}}).

## Кодировки и Reader

Символ ≠ байт. В **UTF-8** латиница занимает 1 байт, кириллица — 2, эмодзи — 4. При побайтовом чтении с приведением `(char) b` каждый байт кириллической буквы становится отдельным «символом» — получаются кракозябры.

`Reader` читает **символы**: он сам декодирует байты по кодировке.

```java
try (Reader reader = new InputStreamReader(new FileInputStream(file), StandardCharsets.UTF_8)) {
    char[] buffer = new char[128];                  // для Reader — char[], а не byte[]
    StringBuilder sb = new StringBuilder();
    int count;
    while ((count = reader.read(buffer)) > 0) {
        sb.append(buffer, 0, count);
    }
}
```

`InputStreamReader` — **мост** от байтов к символам: оборачивает любой `InputStream`.

:::outdated "Кодировка по умолчанию — UTF-8 только с Java 18"
В видео сказано, что ридеры по умолчанию используют UTF-8. Это верно **начиная с Java 18** (JEP 400). Раньше кодировкой по умолчанию была системная: в русской Windows — `windows-1251`, и тот же код давал кракозябры на одной машине и работал на другой. Правило на любую версию: **всегда указывайте кодировку явно** — `StandardCharsets.UTF_8`.
:::

:::warning "Опасность new String(buffer, 0, count) для UTF-8"
Если читать UTF-8-файл **байтами** порциями и превращать каждую порцию в строку, многобайтовый символ может разрезаться границей буфера — получится `�`. Для текста читайте через `Reader` (он учитывает границы символов) или весь файл сразу.
:::

## Что не рассказано в видео

- **`BufferedReader.readLine()`** — классика построчного чтения; `reader.lines()` — стрим строк.
- **Современно:** `Files.readString(path)` (UTF-8 по умолчанию), `Files.readAllLines`, `Files.lines` (ленивый стрим, закрывать в try-with-resources), `Files.newBufferedReader(path, charset)`.
- **`String.split` принимает регулярное выражение:** `split(".")` вернёт пустой массив — точку надо экранировать `split("\\.")`; пробелы — надёжнее `split("\\s+")`. Подробнее — в статье [Regex](#/extra/regex).
