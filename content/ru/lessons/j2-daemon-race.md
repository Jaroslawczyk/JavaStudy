## Потоки-демоны

JVM завершает программу, когда закончились **все основные (не-демон) потоки**. Бесконечный таймер в обычном потоке «держит» программу вечно. Решение — сделать его демоном:

```java
Thread timer = new Thread(() -> {
    try {
        int seconds = 0;
        while (true) {
            System.out.println(seconds++);
            Thread.sleep(1000);
        }
    } catch (InterruptedException ignored) { }
});
timer.setDaemon(true);      // ДО start(), иначе IllegalThreadStateException
timer.start();
```

- Демоны **завершаются автоматически**, когда завершены все основные потоки — **не только `main`** ({{t j2 1:44:25}}).
- Поток наследует «демонность» от создавшего его потока.
- Типичные демоны JVM — потоки сборщика мусора и JIT-компилятора.

:::warning "Демон обрывается на полуслове"
При завершении JVM демоны не получают ни `interrupt()`, ни шанса выполнить `finally`. Никогда не поручайте демону запись в файл или БД — данные останутся недописанными. Демон годится для мониторинга, таймеров, фоновой очистки кеша.
:::

## Состояние гонки (race condition)

```java
public class Counter {
    private int value;
    public void increment() { value++; }
    public void decrement() { value--; }
    public int getValue() { return value; }
}

Counter counter = new Counter();
Thread t1 = new Thread(() -> { for (int i = 0; i < 1000; i++) counter.increment(); });
Thread t2 = new Thread(() -> { for (int i = 0; i < 1000; i++) counter.decrement(); });
t1.start(); t2.start();
t1.join(); t2.join();
System.out.println(counter.getValue());   // 9, 296, -251… но не всегда 0
```

`value++` — это **три** операции: прочитать `value`, прибавить 1, записать обратно. Сценарий потери обновления:

| Шаг | Поток 1 | Поток 2 | `value` |
|---|---|---|---|
| 1 | читает 0 | | 0 |
| 2 | | читает 0 | 0 |
| 3 | пишет 0 + 1 | | 1 |
| 4 | | пишет 0 − 1 | **−1** |

Одно увеличение «потерялось». Результат зависит от того, как планировщик чередует потоки — поэтому он разный при каждом запуске, а в тестах ошибка может не проявляться месяцами.

:::interview "Вопрос с собеседования"
**Что такое race condition?** — Ситуация, когда результат зависит от порядка выполнения потоков, работающих с общими данными. Типичный пример — неатомарная операция «прочитать–изменить–записать» (`count++`). Лечится синхронизацией (`synchronized`, `Lock`), атомиками (`AtomicInteger`) или отказом от общего изменяемого состояния.
:::

## Что не рассказано в видео

- **Data race vs race condition.** Data race — одновременный доступ к переменной без синхронизации, где хотя бы один поток пишет (нарушение модели памяти). Race condition — более широкое понятие: ошибка логики из-за порядка операций (даже с потокобезопасными методами: `if (!map.containsKey(k)) map.put(k, v)` — «проверить-затем-действовать»).
- **Check-then-act** — второй классический вид гонки. Для коллекций используйте атомарные методы: `map.putIfAbsent`, `map.computeIfAbsent`, `map.merge`.
- **Лучшая синхронизация — её отсутствие.** Неизменяемые объекты (`record`, `final`-поля), локальные переменные и разделение данных между потоками убирают гонки на уровне дизайна.
- **Виртуальные потоки всегда демоны** (Java 21+) — `setDaemon(false)` для них бросит исключение.
