**Deadlock** (взаимная блокировка) — ситуация, когда потоки вечно ждут друг друга. Программа не падает и не выдаёт ошибок — она просто «замирает». Воспроизводим deadlock на переводах между двумя счетами и учимся его предотвращать. В домашнем задании — МФУ, которое умеет одновременно печатать и сканировать.

## Как возникает deadlock

```java
public class Account {
    private final Object monitor1 = new Object(), monitor2 = new Object();
    private int amount1, amount2;

    public void transfer1to2(int amount) {
        synchronized (monitor1) {
            sleep(2000);
            synchronized (monitor2) {             // ждём монитор 2
                amount1 -= amount; amount2 += amount;
            }
        }
    }

    public void transfer2to1(int amount) {
        synchronized (monitor2) {
            sleep(2000);
            synchronized (monitor1) {             // ждём монитор 1
                amount2 -= amount; amount1 += amount;
            }
        }
    }
}
```

| Время | Поток 1 (`transfer1to2`) | Поток 2 (`transfer2to1`) |
|---|---|---|
| t1 | захватил монитор 1 | захватил монитор 2 |
| t2 | ждёт монитор 2 ⏳ | ждёт монитор 1 ⏳ |
| ∞ | ждёт… | ждёт… |

### Четыре условия Коффмана

Deadlock возможен, только если выполнены все четыре:
1. **Взаимное исключение** — ресурс может держать только один поток.
2. **Удержание и ожидание** — поток держит один ресурс и ждёт другой.
3. **Нет принудительного освобождения** — ресурс нельзя отобрать.
4. **Циклическое ожидание** — A ждёт B, B ждёт A.

Сломайте любое — и deadlock невозможен.

## Как предотвратить

**1. Единый порядок захвата** (ломает циклическое ожидание) — самый частый способ:

```java
static void transfer(Account from, Account to, int amount) {
    Account first  = from.id < to.id ? from : to;   // всегда сначала меньший id
    Account second = from.id < to.id ? to : from;
    synchronized (first) {
        synchronized (second) {
            from.balance -= amount;
            to.balance += amount;
        }
    }
}
```

**2. Попытка с таймаутом** (ломает «удержание и ожидание») — `ReentrantLock.tryLock(timeout)`: не удалось взять вторую блокировку — отпускаем первую и пробуем позже.

**3. Меньше вложенных блокировок** — один монитор на операцию, неизменяемые данные, очереди сообщений вместо общих объектов.

:::tip "Как найти deadlock в работающей программе"
Снимите дамп потоков: `jstack <pid>` (или `jcmd <pid> Thread.print`, или кнопка «camera» в отладчике IntelliJ). JVM сама пишет в конце: **«Found one Java-level deadlock»** — и показывает, какой поток какой монитор держит и чего ждёт. Также видно в VisualVM и JDK Mission Control.
:::

## Livelock и starvation

- **Livelock** — потоки не заблокированы, но бесконечно уступают друг другу (два человека в коридоре одновременно шагают в одну сторону). Лечится случайной задержкой перед повтором.
- **Starvation (голодание)** — поток не получает ресурс, потому что его постоянно занимают другие. Лечится «честными» блокировками (`new ReentrantLock(true)`) и ограниченными очередями.

:::interview "Вопрос с собеседования"
**Что такое deadlock и как его избежать?** — Взаимная блокировка: каждый из потоков держит ресурс и ждёт ресурс, занятый другим, — ожидание вечное. Избежать: захватывать блокировки всегда в одном порядке, использовать `tryLock` с таймаутом, уменьшать вложенность блокировок. Обнаружить — дампом потоков (`jstack`).
:::
