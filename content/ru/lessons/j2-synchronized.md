## synchronized-метод

```java
public class Counter {
    private int value;
    public synchronized void increment() { value++; }
    public synchronized void decrement() { value--; }
    public synchronized int getValue() { return value; }
}
```

Теперь результат всегда 0: пока один поток выполняет `increment`, другой не может войти **ни в один** `synchronized`-метод этого же объекта.

## Монитор и критическая секция

Аналогия из видео: кабинка в поезде с табличкой «свободно/занято».

- **Критическая секция** — участок кода, где одновременно может находиться только один поток (кабинка).
- **Монитор** (объект синхронизации, lock) — «табличка»: хранит, свободна секция или занята и каким потоком. Монитором может быть **любой объект** — у каждого объекта в Java есть встроенный монитор.

```java
public class Counter {
    private final Object monitor = new Object();
    private int value;

    public void increment() {
        // код до блока может выполняться параллельно
        synchronized (monitor) {          // занять монитор или ждать
            value++;                      // критическая секция
        }                                 // монитор освобождается (даже при исключении)
    }
}
```

| Запись | Монитор |
|---|---|
| `synchronized void m()` | `this` — сам объект |
| `static synchronized void m()` | `Counter.class` — объект класса |
| `synchronized (lock) { … }` | указанный объект `lock` |

## Зачем несколько мониторов

Если в классе два **независимых** счётчика, а все методы синхронизированы по `this`, поток, меняющий первый счётчик, будет зря ждать поток, меняющий второй. Решение — свой монитор для каждой независимой группы данных:

```java
private final Object lock1 = new Object(), lock2 = new Object();
private int value1, value2;

public void increment1() { synchronized (lock1) { value1++; } }
public void increment2() { synchronized (lock2) { value2++; } }
```

В видео такой вариант оказался быстрее: 10 секунд против 16 ({{t j2 2:00:46}}).

:::tip "Правила для мониторов"
- Монитор делайте `private final`: если ссылку на монитор подменить, потоки начнут синхронизироваться по разным объектам (IDEA подсвечивает это предупреждением — {{t j2 2:10:28}}).
- Не синхронизируйтесь по строковым литералам, `Integer` и другим «общим» объектам — их может использовать чужой код.
- Синхронизация по `this` открыта миру: любой внешний код может сделать `synchronized (yourObject)` и помешать вам. Приватный монитор надёжнее.
:::

## Вопросы с собеседований

:::interview "Чем synchronized-метод отличается от обычного?"
Его одновременно может выполнять только один поток (на один и тот же монитор). {{t j2 2:01:00}}
:::

:::interview "Что такое монитор и что может им быть?"
Объект, по которому синхронизируются потоки: если монитор занят, поток ждёт его освобождения. Монитором может быть любой объект. У `synchronized`-метода монитор — `this`, у статического — объект `Class`. {{t j2 2:01:11}}
:::

:::interview "Какие методы могут работать одновременно?"
Метод 1 без синхронизации, методы 2 и 3 по одному монитору, метод 4 — по другому. Одновременно могут выполняться 1, 2, 4 или 1, 3, 4: методы 2 и 3 друг друга блокируют. {{t j2 2:01:49}}
:::

## Что не рассказано в видео

- **Реентерабельность.** Поток, уже владеющий монитором, может снова войти в `synchronized` по тому же монитору (например, один `synchronized`-метод вызывает другой) — сам себя он не заблокирует.
- **Видимость.** `synchronized` гарантирует не только взаимное исключение, но и то, что изменения, сделанные внутри блока, увидит следующий поток, захвативший тот же монитор (happens-before). Поэтому **чтение** общего поля (`getValue()`) тоже надо синхронизировать.
- **`ReentrantLock`** из `java.util.concurrent.locks` — явная блокировка с `tryLock(timeout)`, прерываемым ожиданием и честной очередью. Всегда освобождается в `finally`:

```java
private final ReentrantLock lock = new ReentrantLock();
public void increment() {
    lock.lock();
    try { value++; } finally { lock.unlock(); }
}
```

- **`ReadWriteLock`** — много читателей одновременно, писатель — один.

:::note "Виртуальные потоки и synchronized"
В Java 21–23 виртуальный поток, заблокированный внутри `synchronized`, «прикалывал» (pinning) поток-носитель, поэтому советовали `ReentrantLock`. **С Java 24 (JEP 491) эта проблема решена**, и `synchronized` с виртуальными потоками снова можно использовать без опасений.
:::
