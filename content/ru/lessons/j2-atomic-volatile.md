Ещё два инструмента против проблем многопоточности: **атомарные типы** (`AtomicInteger` и компания) — операции «прочитать-изменить-записать» за один неделимый шаг, и ключевое слово **`volatile`** — гарантия видимости изменений между потоками. И разбор популярного заблуждения: `volatile` **не** решает гонку.

## Атомарные типы

```java
public class Counter {
    private final AtomicInteger value = new AtomicInteger();

    public void increment() { value.incrementAndGet(); }
    public void decrement() { value.decrementAndGet(); }
    public int getValue()   { return value.get(); }
}
```

Никакого `synchronized`, а результат всегда 0. Пакет `java.util.concurrent.atomic`: `AtomicInteger`, `AtomicLong`, `AtomicBoolean`, `AtomicReference<V>`, массивы `AtomicIntegerArray`…

| Метод | Что делает |
|---|---|
| `get()` / `set(v)` | Прочитать / записать |
| `incrementAndGet()` / `getAndIncrement()` | `++i` / `i++` атомарно |
| `addAndGet(delta)` | Прибавить |
| `compareAndSet(expected, new)` | Записать `new`, только если сейчас `expected` |
| `updateAndGet(x -> x * 2)` | Произвольная функция (Java 8+) |
| `accumulateAndGet(x, Math::max)` | Свернуть с аргументом |

### Как это работает: CAS

Атомики построены не на блокировках, а на инструкции процессора **CAS** (compare-and-swap): «запиши новое значение, если в памяти всё ещё старое; иначе сообщи о неудаче». При неудаче операция просто повторяется:

```java
int prev, next;
do {
    prev = value.get();
    next = prev + 1;
} while (!value.compareAndSet(prev, next));
```

Это **неблокирующий** (lock-free) алгоритм: потоки не засыпают, а «крутятся». При умеренной конкуренции он быстрее `synchronized`.

:::tip "LongAdder для горячих счётчиков"
Если десятки потоков постоянно увеличивают один счётчик (метрики, статистика), `AtomicLong` упирается в постоянные повторы CAS. **`LongAdder`** (Java 8) хранит несколько ячеек и складывает их при чтении — под высокой нагрузкой он в разы быстрее.
:::

## volatile

Объяснение из видео: поток может закэшировать переменную у себя и не видеть изменений, сделанных другими потоками; `volatile` запрещает такое кэширование. Это хорошая интуиция. Точнее (по модели памяти Java, JMM):

- **Видимость.** Запись в `volatile`-поле сразу видна всем потокам, которые его читают.
- **Упорядочивание.** Всё, что поток записал **до** записи в `volatile`-поле, станет видно потоку, который **после** прочитает это поле (отношение *happens-before*). Компилятор и процессор не переставят операции через эту границу.
- **Атомарность** — только для отдельного чтения/записи (включая `long`/`double`). **Составные операции (`count++`) не становятся атомарными.**

```java
private volatile boolean running = true;     // классический случай: флаг остановки

public void run() {
    while (running) { doWork(); }            // без volatile цикл мог бы не увидеть false
}
public void stop() { running = false; }
```

:::warning "Поправка к видео"
Автор советует делать `volatile` **любую** переменную, к которой обращаются разные потоки. Это не нужно, если все обращения уже идут внутри `synchronized` по одному монитору (или через `Lock`) — синхронизация сама даёт видимость. `volatile` нужен там, где синхронизации нет: флаги, однократно публикуемые ссылки, double-checked locking.
:::

:::interview "Вопрос с собеседования"
**Что делает volatile и решает ли он race condition?** — Гарантирует видимость записи всем потокам и запрещает переупорядочивание вокруг обращения к полю. Атомарности составных операций не даёт: `volatile int count; count++` по-прежнему теряет обновления. Для счётчиков — `AtomicInteger`/`LongAdder` или синхронизация.
:::

## Что не рассказано в видео

- **Double-checked locking** — ленивая инициализация с `volatile`:

```java
private static volatile Service instance;
static Service get() {
    Service s = instance;
    if (s == null) {
        synchronized (Service.class) {
            s = instance;
            if (s == null) instance = s = new Service();
        }
    }
    return s;
}
```

Без `volatile` другой поток может получить ссылку на **не до конца сконструированный** объект.

- **`VarHandle`** (Java 9) — низкоуровневый доступ к полям с разными режимами памяти; на нём построены современные атомики.
- Глубже о модели памяти — статья [JMM и volatile](#/extra/jmm-volatile).

## Домашнее задание

В видео заданий нет — вот свои.

:::task easy "Атомарный счётчик"
Перепишите `Counter` на `AtomicInteger`. Запустите 8 потоков по 1 000 000 инкрементов и проверьте результат. Сравните время с `synchronized`-версией.
:::

:::task medium "Флаг без volatile"
Напишите поток с циклом `while (!stop) { counter++; }` (без `sleep` и вывода внутри!) и остановите его из `main` через секунду, установив `stop = true`. Запустите с `volatile` и без. Без него программа может зависнуть навсегда — объясните почему (подсказка: JIT вынес чтение из цикла).
:::

:::task medium "CAS вручную"
Реализуйте метод `static int incrementIfLessThan(AtomicInteger a, int limit)` на цикле `compareAndSet`: увеличивает значение, только если оно меньше `limit`, и возвращает новое значение. Проверьте 10 потоками, что значение никогда не превышает лимит.
:::

:::task hard "AtomicLong против LongAdder"
Сделайте бенчмарк (лучше на JMH): 1, 4, 16 потоков инкрементируют общий счётчик 10 млн раз. Сравните `synchronized`, `AtomicLong`, `LongAdder`. Постройте таблицу и объясните, почему при росте числа потоков разрыв увеличивается.
:::
