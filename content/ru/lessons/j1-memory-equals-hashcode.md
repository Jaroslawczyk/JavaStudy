## Стек и куча

```java
int number = 5;                     // стек: number = 5
Car car1 = new Car("BMW", 1);       // стек: car1 = адрес → куча: объект Car
Car car2 = car1;                    // стек: car2 = тот же адрес
```

| | Стек (stack) | Куча (heap) |
|---|---|---|
| Что хранится | Локальные переменные: примитивы и **ссылки** | Все **объекты**, созданные через `new` (и массивы) |
| Чей | У каждого потока свой | Один на всю JVM, общий для всех потоков |
| Размер | Небольшой (обычно ~1 МБ на поток, флаг `-Xss`) | Большой, ограничен флагом `-Xmx` (по умолчанию ≈ ¼ ОЗУ) |
| Очистка | Автоматически при выходе из метода | Сборщик мусора (GC) |
| Ошибка при переполнении | `StackOverflowError` (например, бесконечная рекурсия) | `OutOfMemoryError: Java heap space` |

Поэтому `car1 == car2` сравнивает **значения в стеке** — то есть адреса. Для примитивов это и есть сами значения, а для объектов — ответ на вопрос «это один и тот же объект?».

## Сборщик мусора (Garbage Collector)

```java
Car car1 = new Car("BMW", 1);
Car car2 = new Car("BMW", 1);
car2 = car1;     // на второй объект больше никто не ссылается — он станет мусором
```

GC удаляет объекты, **до которых нельзя добраться** от «корней»: локальных переменных в стеках потоков, статических полей, активных потоков. Поэтому:

- два объекта, ссылающихся **только друг на друга**, будут удалены — до них не дойти от корней. Java использует **трассирующий** GC, а не подсчёт ссылок, поэтому циклы ему не мешают;
- вызывать GC вручную (`System.gc()`) не нужно — это лишь «просьба», JVM решает сама.

:::note "Уточнение к видео"
В видео говорится «объект удаляется, когда на него нет ссылок из стека». Это упрощение: корнями (GC roots) служат ещё и статические поля классов, JNI-ссылки, потоки. Объект, на который ссылается `static`-поле, не удалится никогда — классический источник утечек памяти. Сборщик по умолчанию сегодня — **G1** (а с Java 27 — во всех окружениях); для минимальных пауз есть **ZGC**.
:::

## equals — сравнение по содержимому

Метод `equals` унаследован от `Object`, и по умолчанию он делает то же, что `==`, — сравнивает ссылки. Чтобы сравнивать по полям, его **переопределяют**:

```java
@Override
public boolean equals(Object o) {
    if (this == o) return true;                       // тот же объект
    if (o == null || getClass() != o.getClass()) return false;
    Car car = (Car) o;
    return number == car.number && Objects.equals(brand, car.brand);
}
```

### Контракт equals

1. **Рефлексивность**: `x.equals(x)` — `true`.
2. **Симметричность**: если `x.equals(y)`, то и `y.equals(x)`.
3. **Транзитивность**: `x.equals(y)` и `y.equals(z)` → `x.equals(z)`.
4. **Согласованность**: повторные вызовы дают тот же результат, пока объекты не менялись.
5. `x.equals(null)` — всегда `false`.

## hashCode — числовое представление объекта

`hashCode()` возвращает `int`, по которому хеш-коллекции (`HashSet`, `HashMap`) быстро находят «корзину» для объекта.

```java
@Override
public int hashCode() {
    return Objects.hash(brand, number);
}
```

### Правила equals и hashCode

1. **Переопределил `equals` — переопредели `hashCode`.** Иначе равные объекты получат разные хеш-коды, и `HashSet` будет хранить «дубликаты», а `HashMap` не найдёт ключ.
2. Если объекты **равны** по `equals` → хеш-коды **обязаны** совпадать.
3. Если хеш-коды **разные** → объекты точно разные.
4. Если хеш-коды **совпали** → объекты могут быть разными — это **коллизия** (хеш-кодов ~4,3 млрд, а объектов может быть сколько угодно).

<kbd>Alt+Insert</kbd> → **equals() and hashCode()** — IDEA сгенерирует оба метода по выбранным полям.

## Что не рассказано в видео

### getClass() или instanceof?

Сгенерированный IDEA код проверяет `getClass() != o.getClass()` — объект подкласса не будет равен объекту родителя. Вариант с `instanceof` допускает подклассы, но легко нарушает **симметричность**. Без веской причины используйте `getClass()` или делайте класс `final`.

### Records делают это за вас

```java
public record Car(String brand, int number) { }
// equals, hashCode и toString сгенерированы автоматически по всем полям
```

### Строки и пул строк

Строковые **литералы** с одинаковым текстом JVM хранит в **пуле строк** (string pool) в одном экземпляре, поэтому `"BMW" == "BMW"` случайно даёт `true`. Но строка из ввода, файла или после склейки — новый объект. Поэтому строки — только через `equals`. У `String` хеш-код вычисляется один раз и кэшируется.

### Не кладите изменяемые поля в hashCode ключа

Если поле, участвующее в `hashCode`, изменить у объекта, который уже лежит в `HashSet`/`HashMap`, объект «потеряется» в коллекции. Подробно — в уроке о `HashMap`.

## Вопросы с собеседований

:::interview "Из видео"
1. **Как устроена память в Java?** — Примитивы и ссылки на объекты — в стеке (у каждого потока свой), сами объекты — в куче.
2. **Когда сборщик мусора удаляет объект?** — Когда объект недостижим от GC roots (стек, статические поля, потоки).
3. **Удалит ли GC два объекта, ссылающиеся только друг на друга?** — Да, если до них нельзя добраться от корней.
4. **Почему нельзя сравнивать строки и объекты через `==`?** — `==` сравнивает ссылки (адреса), а не содержимое.
5. **Как сравнить объекты по полям?** — Переопределить `equals` (и вместе с ним `hashCode`).
6. **Какие правила у equals и hashCode?** — Переопределил `equals` → переопредели `hashCode`; равные объекты — равные хеш-коды; разные хеш-коды — разные объекты; равные хеш-коды не гарантируют равенства (коллизия).
:::
