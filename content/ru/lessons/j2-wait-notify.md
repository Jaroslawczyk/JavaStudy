## Активное ожидание — плохо

```java
while (true) {
    Runnable task = queue.take();      // возвращает null, если пусто
    if (task != null) new Thread(task).start();
}
```

Цикл крутится без остановки, даже если задач нет: 100 % одного ядра, разряженная батарея телефона. Это называется **busy waiting** (активное ожидание).

## wait() и notify()

```java
public class MyBlockingQueue {
    private final Object monitor = new Object();
    private final Queue<Runnable> queue = new LinkedList<>();

    public void put(Runnable task) {
        synchronized (monitor) {
            queue.add(task);
            monitor.notify();                 // разбудить ожидающего
        }
    }

    public Runnable take() throws InterruptedException {
        synchronized (monitor) {
            while (queue.isEmpty()) {         // именно while, не if!
                monitor.wait();               // уснуть и ОТПУСТИТЬ монитор
            }
            return queue.poll();
        }
    }
}
```

- `wait()` — поток засыпает (состояние `WAITING`) и **освобождает монитор**, поэтому другой поток может войти в `put`.
- `notify()` — будит **один** произвольный поток, ждущий на этом мониторе; `notifyAll()` — **всех**. Проснувшийся поток сначала снова захватывает монитор, затем продолжает с места, где уснул.
- Методы объявлены в `Object` — потому что монитором может быть любой объект.
- Вызывать их можно **только внутри `synchronized` по тому же объекту**, иначе `IllegalMonitorStateException`.

:::warning "Почему while, а не if"
1) Бывают **ложные пробуждения** (spurious wakeups) — поток может проснуться без `notify`. 2) Пока проснувшийся поток ждал монитор, задачу мог забрать другой. Условие всегда перепроверяют в цикле.
:::

## notify или notifyAll

В задаче `ABC` три потока ждут на одном мониторе, но каждому нужно своё условие («сейчас моя буква»). `notify()` может разбудить «не того» — тот проверит условие, снова уснёт, а нужный поток так и не проснётся: программа зависнет ({{t j2 3:10:37}}). `notifyAll()` будит всех — каждый проверит условие, и ровно один продолжит.

Правило: `notify()` безопасен, только если все ожидающие ждут **одного и того же** условия и любой из них может продолжить. Иначе — `notifyAll()` (или `Condition` с отдельными очередями ожидания).

## Готовое решение: BlockingQueue

```java
BlockingQueue<Runnable> queue = new LinkedBlockingQueue<>();
queue.put(task);                 // ждёт, если очередь полна (для ограниченной)
Runnable next = queue.take();    // ждёт, если пусто — никогда не вернёт null
```

| Метод | Полная/пустая очередь |
|---|---|
| `put` / `take` | Ждёт |
| `offer` / `poll` | Сразу возвращает `false`/`null` |
| `offer(e, t, unit)` / `poll(t, unit)` | Ждёт не дольше таймаута |

Реализации: `ArrayBlockingQueue` (ограниченная), `LinkedBlockingQueue`, `PriorityBlockingQueue`, `DelayQueue`, `SynchronousQueue` (без буфера — передача «из рук в руки»). Именно на `BlockingQueue` построены пулы потоков из прошлого урока.

:::interview "Вопросы с собеседования"
**Что делает `wait()`?** — Переводит поток в ожидание и отпускает монитор, пока его не разбудят `notify`/`notifyAll` или `interrupt`.

**Чем отличаются `notify()` и `notifyAll()`?** — `notify` будит один ждущий поток, `notifyAll` — все; проснувшиеся по очереди захватывают монитор.

**Почему эти методы в `Object`, а не в `Thread`?** — Ждут не поток, а монитор, а монитором может быть любой объект.
:::

## Что не рассказано в видео

- **`Lock` + `Condition`** — современная замена `wait/notify`: несколько условий на одной блокировке (`notFull`, `notEmpty`) и `signal()` нужной группе потоков.
- **Producer–consumer** — классический паттерн «производитель–потребитель»; в реальном коде его почти всегда пишут на `BlockingQueue`, а не на голых `wait/notify`.
