**Модель памяти Java** (Java Memory Model, JMM) определяет, когда изменения, сделанные одним потоком, становятся видны другим. Видео объясняет `volatile` через «кэш потока» — это полезная интуиция, но на собеседованиях Middle+ ждут понятий **видимость**, **переупорядочивание** и **happens-before**.

## Почему вообще возникают проблемы

1. **Кэши процессора.** У каждого ядра свои кэши; запись одного ядра не мгновенно видна другому.
2. **Переупорядочивание.** Компилятор, JIT и процессор переставляют независимые инструкции ради скорости. В одном потоке результат не меняется, но другой поток может увидеть операции «в другом порядке».
3. **Оптимизации JIT.** Чтение поля в цикле может быть вынесено из цикла, если JIT «уверен», что поле не меняется.

```java
// без синхронизации поток может НИКОГДА не завершиться
static boolean ready;
static int value;

// поток 1                // поток 2
value = 42;               while (!ready) { }
ready = true;             System.out.println(value);   // может напечатать 0!
```

## Happens-before

JMM гарантирует: если действие **A happens-before B**, то все записи до A видны в B. Основные правила:

| Правило | A happens-before B |
|---|---|
| Порядок программы | каждое действие потока → следующее действие того же потока |
| Монитор | выход из `synchronized(m)` → последующий вход в `synchronized(m)` |
| volatile | запись в volatile-поле → последующее чтение этого поля |
| Запуск потока | `t.start()` → любое действие в `t` |
| Завершение потока | любое действие в `t` → возврат из `t.join()` |
| Транзитивность | A → B и B → C ⇒ A → C |

Также `java.util.concurrent` даёт свои гарантии: `put` в `ConcurrentHashMap` → `get`, `countDown` → возврат из `await`, `submit` задачи → её выполнение, завершение задачи → `future.get()`.

## volatile

```java
static volatile boolean ready;
static int value;

value = 42;          // 1
ready = true;        // 2 — volatile-запись: всё, что выше, «публикуется»

while (!ready) { }   // volatile-чтение
System.out.println(value);   // гарантированно 42
```

`volatile` даёт **видимость** и **запрет переупорядочивания** вокруг обращений к полю, но **не атомарность** составных операций (`count++`). Подробно — в [уроке об атомиках и volatile](#/lessons/j2-atomic-volatile).

## final-поля и безопасная публикация

Поля `final` имеют особую гарантию: если ссылка на объект не «утекла» из конструктора, любой поток, получивший ссылку, увидит корректно инициализированные `final`-поля — даже без синхронизации. Поэтому **неизменяемые объекты потокобезопасны «бесплатно»**.

Способы безопасно опубликовать объект: инициализация в `static`-поле (через инициализацию класса), запись в `volatile`-поле или `AtomicReference`, передача через потокобезопасную коллекцию, публикация внутри `synchronized`.

:::warning "Не выпускайте this из конструктора"
Регистрация `this` как слушателя или запуск потока, использующего `this`, прямо в конструкторе может отдать другим потокам не до конца созданный объект — гарантия для `final`-полей при этом теряется.
:::

## Атомарность long и double

Запись в обычное (не volatile) поле `long`/`double` по спецификации может быть не атомарной (два 32-битных половинки). На 64-битных JVM это практически не встречается, но `volatile long` гарантирует атомарность чтения/записи формально.

:::interview "Вопросы с собеседования"
**Что такое happens-before?** — Отношение порядка в модели памяти: если A happens-before B, результаты A видны B. Возникает через `synchronized`, `volatile`, `start/join`, классы `java.util.concurrent` и транзитивность.

**Почему неизменяемые объекты потокобезопасны?** — Их состояние не меняется после конструктора, а семантика `final`-полей гарантирует, что другие потоки увидят их корректно инициализированными.
:::
