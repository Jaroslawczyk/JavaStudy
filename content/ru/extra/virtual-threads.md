**Виртуальные потоки** (Java 21, JEP 444) — главное изменение многопоточности в Java за последние годы. Это лёгкие потоки, которыми управляет JVM, а не операционная система. Их можно создать миллион, и они позволяют писать простой блокирующий код «поток на запрос», который масштабируется как асинхронный.

## Проблема платформенных потоков

Обычный `Thread` = поток ОС: ~1 МБ стека, дорогое создание и переключение. Сервер с пулом в 200 потоков обслуживает максимум 200 одновременных запросов — даже если каждый 95 % времени просто **ждёт** ответа от базы или внешнего API. Раньше это решали реактивным программированием (WebFlux, `CompletableFuture`), но такой код сложно писать, читать и отлаживать.

## Как работают виртуальные потоки

- Виртуальный поток выполняется на **потоке-носителе** (carrier thread) из небольшого `ForkJoinPool` (по числу ядер).
- Когда виртуальный поток блокируется на I/O (`socket.read`, JDBC, `Thread.sleep`, `BlockingQueue.take`), JVM **снимает** его с носителя (unmount), сохраняя стек в куче, и запускает на носителе другой виртуальный поток.
- Когда данные пришли, поток снова монтируется на какой-то носитель и продолжает работу.

```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    IntStream.range(0, 100_000).forEach(i ->
        executor.submit(() -> {
            Thread.sleep(Duration.ofSeconds(1));     // блокирующий вызов — и это нормально
            return i;
        }));
}   // 100 000 задач завершатся примерно за секунду

Thread.ofVirtual().name("worker-", 0).start(task);
Thread.startVirtualThread(task);
```

## Правила использования

| ✅ Делайте | ❌ Не делайте |
|---|---|
| Новый виртуальный поток на каждую задачу | Пулы виртуальных потоков — они дешёвые, пулить незачем |
| Блокирующий код: JDBC, `HttpClient`, `sleep` | Ждать ускорения CPU-задач — ядер столько же |
| Ограничивать доступ к ресурсу `Semaphore` (например, 50 соединений к БД) | Ограничивать параллельность размером пула |
| `ReentrantLock` или `synchronized` (Java 24+) | Огромные объекты в `ThreadLocal` — их будут миллионы копий |

:::outdated "Pinning и synchronized"
В Java 21–23 блокировка внутри `synchronized` «прикалывала» (pinning) виртуальный поток к носителю, и под нагрузкой носители заканчивались. Совет «заменяйте `synchronized` на `ReentrantLock`» был актуален до **Java 24** — JEP 491 убрал эту проблему. Прикалывание остаётся только при вызове нативного кода (JNI) и в редких случаях; диагностика — событие JFR `jdk.VirtualThreadPinned`.
:::

## Во фреймворках

- **Spring Boot 3.2+**: `spring.threads.virtual.enabled=true` — Tomcat/Jetty, `@Async`, планировщики переходят на виртуальные потоки.
- **Quarkus**: аннотация `@RunOnVirtualThread`.
- **Helidon 4** построен на виртуальных потоках целиком.

Для типичного REST-сервиса «запрос → БД → внешний API → ответ» это часто означает рост пропускной способности без переписывания кода.

## Рядом: Structured Concurrency и Scoped Values

- **Scoped Values** (финализированы в Java 25, JEP 506) — неизменяемая замена `ThreadLocal` для передачи контекста (пользователь, trace-id) вглубь вызовов, удобная для миллионов потоков.
- **Structured Concurrency** (`StructuredTaskScope`) — запуск подзадач как единого целого с общей отменой при ошибке. На 2026 год API всё ещё в preview.

:::interview "Вопросы с собеседования"
**Чем виртуальный поток отличается от платформенного?** — Платформенный — обёртка над потоком ОС, тяжёлый и ограниченный по количеству. Виртуальный управляется JVM, монтируется на поток-носитель только пока выполняет код, при блокировке на I/O освобождает носитель; их можно создавать миллионами.

**Ускорят ли виртуальные потоки сортировку большого массива?** — Нет: они помогают задачам, которые ждут (I/O-bound), а не вычислительным (CPU-bound).
:::
